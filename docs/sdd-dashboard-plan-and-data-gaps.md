# SDD 基础看板开发计划与上传数据缺口

## 直接答案

沿用已确认的 **PostgreSQL + NAS/NFS + T+1** 方向，复用现有看板页面，开发顺序为：**最小数据合同 → 上传 → 解析处理 → 双路存储 → 聚合发布 → 页面查询与证据下钻**。本文件是简版待实施计划，不表示后端已接通或评审准入条件已关闭。

目前实现的是页面和演示交互：入口加载 `dashboard.html`，指标由静态数据计算，上传通过定时器模拟。架构评审中的“已有基础”指方案已有字段或事件承接位置，不代表真实 TAR 已包含这些数据。当前仓库没有真实 TAR、`upload_payload.json` 样本或生产者实现可核对。[页面入口](../app/page.tsx#L1)、[演示指标](../public/dashboard.html#L1220)、[模拟上传](../public/dashboard.html#L1381)、[评审边界](../public/sdd-architecture-gap-review.html#boundary-title)（源码 L1091–1101）。

评审的 23 项数据需求中，**9 项明确缺少、8 项条件性、6 项已有方案基础**。建议首版先完成导入中心、Session 证据和有可靠来源的基础统计；其余卡片保留入口并显示“缺数据 / 未接入”，待相应输入和口径齐备后启用真实数值。[原始缺口矩阵](../public/sdd-architecture-gap-review.html#gap)（源码 L960–1003）。

## 简版开发计划

| 顺序 | 开发内容 | 基本验收 |
| --- | --- | --- |
| 0. 补齐最小数据合同 | 用真实样包确认 `upload_payload.json + session.tar.gz` 配对方式、Schema 版本、Artifact manifest、身份关系、时间与阶段口径；逐项确定首版指标来源及缺失处理。把评审尚未确定的幂等、部分成功、迟到回补及访问边界落实为规则。 | 一份样包能对应到要展示的字段；缺少的字段明确列出；不会把 Session 数自动当作 Task 数。 |
| 1. 上传 | 给现有导入中心接真实上传接口；接收并配对两个文件，校验大小、SHA 和基础格式，生成上传记录；支持状态查询及失败重试，同一次重复上传不重复计数。 | 刷新页面后记录仍在；完整且校验通过的包才进入待处理；上传完成时主看板不提前更新。 |
| 2. 处理 | 定时任务选取待处理上传，流式扫描 TAR；校验路径和解包限额；解析结构化 JSON/CSV，识别日志、分析、Cards、KU 和 HTML；记录字段缺失、解析版本、错误与处理结果。 | 合格包产生可追溯的 Session/Stage 事实和文件清单；坏包明确失败，缺字段可定位；部分成功按第 0 步确定的规则处理。 |
| 3. 存储 | PostgreSQL 保存身份、上传/处理状态、事实、校验结果及 Artifact 索引；NAS/NFS 保存 Raw、Trace、分析和报告文件，索引使用相对 object key；落实双写失败恢复及校验后的临时包清理。 | 每条事实能找到来源文件；证据可下载；失败重试不重复入库；未确认持久化完整前不清理传输包。 |
| 4. 聚合与发布 | 从合格事实计算日/月指标、分布和可支持的改进汇总；生成带业务日期、输入集合和版本的快照，完成后原子发布。沿用评审中的 01:00 处理、06:00 发布目标，时区和迟到规则在第 0 步定稿。 | 同一快照的总数与下钻明细一致；重跑不重复累计；发布失败保留上一份已发布快照；缺失值不算成 0。 |
| 5. 展示与联调 | 复用管理概览、改进分析、Self-Improving、导入中心和 Task/Session 抽屉，改为调用查询 API；展示快照日期、数据覆盖及缺失原因；报告按对应 Session 打开并落实权限与 HTML 隔离。 | 一份真实样包能走通上传到发布再到证据下钻；筛选结果来自数据库；不再用静态比例缩放冒充真实指标。 |

技术上先采用一个后端应用承载上传、查询和批处理逻辑，批处理以独立进程运行即可；这是简化实施的建议，不要求按评审泳道拆成多个服务。V1 沿用无需 Kafka 的结论。服务部署须具备 PostgreSQL、NAS/NFS 和定时执行条件，现有网页可发布不等于这些运行条件已经具备。[流程与存储分工](../public/sdd-architecture-gap-review.html#architecture)（源码 L771–947）。

首版建议先交付“真实导入 + 证据查询”，再启用已补齐身份与执行事实的任务数、完成率、耗时等指标。一次性准确率、AI 代码归属和改进实际效果按下表补齐后接入。正式实施前，仍需关闭原评审列出的六组准入项，包括上传安全、容量和备份恢复；本计划没有替代该决议。[评审准入项](../public/sdd-architecture-gap-review.html#decision-title)（源码 L1079–1087）。

## 看板数据与上传数据的对应缺口

以下“上传数据”包含配套 payload、TAR 内结构化文件与证据文件。**分类沿用评审，补齐方是本计划的职责建议**；字段名表示需要的信息，不能视为已经冻结的最终 Schema。上传时间、解析状态、覆盖率和快照属于平台生成数据，不要求全由 TAR 携带。

### 明确缺少：需要新增事实来源（9 项）

| 看板数据 | 现方案能够提供什么 | 还缺什么 | 建议补齐方 |
| --- | --- | --- | --- |
| 部门、团队、代码仓筛选 | Session ID 与上传元数据 | `department_id`、`team_id`、`repository_id` 及归属有效期，不能用包名推断组织。 | 上报端携带稳定 ID；组织/仓库主数据维护归属。 |
| 活跃用户数 | 没有稳定执行者身份 | `actor_id`、执行者类型、活动时间；后端定义活跃窗口和去重规则。 | 上报端 + 聚合端。 |
| Task / Spec / Session 下钻关系 | `session_id`、`session_trace_id` | `task_id`、任务名、`spec_id`、`attempt_id` 及一对多关系。 | SDD 执行端。 |
| 任务完成率、任务执行状态 | 上传、处理、发布状态 | 执行结果、完成判定来源、多 attempt 归并方式及有效任务分母；上传成功不能代表执行成功。 | SDD 执行端提供结果；聚合端按口径归并。 |
| Spec / Plan / Code 一次性准确率 | 无 first-attempt 和质量 verdict | 首次尝试边界、DT/test/review 判定、重试次数、分子和分母。 | 执行/测试/评审系统 + 聚合端。 |
| 平均生成代码量、代码量分布 | 可以保存文件 | base/head SHA、增加/删除行数、语言、Agent/人工归属与计量版本；文件总行数不等于生成代码量。 | 代码差异采集端 + 执行端关联信息。 |
| 阶段产出：文档行数、Plan 数、计划项、修改文件数 | 可以保存最终产物 | `output_fact`、产物类型和数量、所属阶段、关联文件及计量口径。 | SDD 执行端；解析端提取确定性数量。 |
| Self-Improving 实际效果 | Experience Cards、Knowledge Units 文件 | 干预 ID、知识版本、后续使用事件、基线/复测对象和测量窗口。只有知识产出不能证明实际效果。 | 知识消费/执行端 + 复测分析端。 |
| 实际货币成本 | Token fact 尚未正式约定，未提供价格 | 模型/provider/version、Token 分类、价格版本、币种、计费规则。此项是原评审的扩展需求，当前概览未显示独立货币成本卡片。 | 调用计量端 + 定价数据；建议后续接入。 |

来源：[明确缺少的原评审条目](../public/sdd-architecture-gap-review.html#L979)（L979–987）；当前页面的阶段质量、概览、改进效果分别见 [质量表数据](../public/dashboard.html#L1446)、[概览 KPI](../public/dashboard.html#L1476)、[改进效果展示](../public/dashboard.html#L1511)。

### 条件性：已有线索，但需要确认字段或计算规则（8 项）

| 看板数据 | 当前候选来源 | 还缺什么 | 建议补齐方 |
| --- | --- | --- | --- |

| 问题现象、根因、措施、当前判断 | 分析 Artifact 中可能有自然语言 | 稳定结构、证据引用、模型推断/人工确认/事实的区分及确认者。 | 分析生产者/确认者；解析端保留判断来源。 |

## 对接时优先消除的两个不一致

1. **包、批次和任务的粒度。** 评审按一个 Session 产出两文件描述，导入演示的一条 Batch 却可以包含几十个 Task，还出现 `manifest.json` 缺失的演示错误。需用真实样包确认“一包一 Session”还是“一包多 Session”，以及 Batch 是上传分组还是夜间处理批次；不能直接照着演示对象建表。[两文件打包](../public/sdd-architecture-gap-review.html#L804)、[演示批次](../public/dashboard.html#L1137)。
2. **阶段的映射。** 页面质量摘要是 Spec / Plan / Code 三项，执行分析是 New Spec / Design / Plan / Implement 四项。需要按执行端阶段分类明确映射和聚合规则；不能将某套 SDD 的阶段列表硬编码成所有上传包的合同。[质量摘要](../public/dashboard.html#L1446)、[执行分析阶段](../public/dashboard.html#L1437)。

## 边界与验证

- **已确认：** 架构方向与缺口分类来自指定评审；当前入口、静态数据、模拟上传及固定报告链接已按本地源码核对。这里的“处理、存储、发布”都是待开发能力。
- **未覆盖：** 未获得真实包、生产者源码、正式 Schema、数据库或 NAS/NFS 运行实例。因此不能断言真实 TAR 一定缺少某个物理字段；本文所述缺口是“现有合同未证明足以支持看板”。
- **最小后续验证：** 先用一份真实样包逐项核对本表并确定第 0 步规则，再验证正常导入、重复上传、字段缺失和处理失败重试，最终检查发布快照与下钻证据一致。安全、容量和恢复验证按原评审的实际上线边界完成。
- **交付范围：** 本次仅编写简版计划与数据缺口，不修改网页或实施服务，不把建议的首版分期记为已经批准的产品合同。
