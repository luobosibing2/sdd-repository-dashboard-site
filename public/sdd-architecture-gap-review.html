THE CENTRAL GAP表名已经有了，事实还没有。

现方案列出了 session_metrics、stage_metrics、daily_metrics、monthly_metrics 和 improvement_item，但没有冻结事实粒度、主键、维度、分子分母、时间口径、来源字段、UNKNOWN 语义与 transformation version。因此它能说明“指标存在哪里”，还不能说明“指标为什么是这个值”。

缺少部门与组织筛选只有 session_id 和上传元数据。Session 无法归属部门、团队、代码仓；同名组织和人员转岗也无法处理。department_id · team_id · repository_id · 有效期
缺少活跃用户数没有稳定的用户或执行者身份。不能去重，也没有“活跃”的时间窗口和资格规则。actor_id · actor type · activity timestamp · active rule
缺少Task / Spec / Session 关系只有 session_id、session_trace_id。不能下钻到 Task/Spec，也不能证明一个 Session 就是一条看板任务。task_id · task_name · spec_id · attempt_id · cardinality
缺少任务完成率与执行状态有上传、处理、发布状态。流水线状态不等于任务完成；缺少完成权威和多 attempt 归并规则。execution_status · terminal outcome · completion authority · denominator rule
缺少阶段一次性准确率没有 first-attempt 或质量 verdict。无法计算 Spec / Plan / Code 首次生成是否通过。attempt boundary · DT/test/review verdict · numerator/denominator · retry count
缺少生成代码量与分布Artifact 可以保存文件，但没有代码产出 fact。无法区分原有代码、Agent 生成、人工修改、返工和删除。base/head SHA · added/deleted LOC · language · provenance · measurement version
缺少阶段产出规模没有文档行数、Plan 数、计划项数和阶段文件关系。最终目录不能可靠回答“哪个阶段产出了多少”。output_fact · stage key · output type · quantity · file relation
缺少Self-Improving 实际效果可以保存 Experience Cards 和 Knowledge Units。产出知识不等于后续任务使用了知识，更不等于效果可归因。intervention ID · KU/Card version · usage event · baseline/retest cohort · measurement window
缺少实际货币成本方案没有正式 Token fact，也没有价格数据。Token 数不能直接换算成本；模型、缓存、推理 Token 和费率会变化。model/provider/version · token categories · price version · currency · billing rule
条件性SDD 任务数可以统计 Session 数。只有在“一 Task = 一 Session”且 attempt 去重后才成立。Task identity · Session relation · deduplication · valid-task rule

条件性Top 改进事务已有 process_anomalies 和宽泛的 improvement_item。缺 taxonomy、去重键、严重度规则、影响分母、证据强度和排序公式。issue occurrence · taxonomy version · severity rubric · affected object · rank version
条件性问题根因与改进措施分析 Artifact 里可能有自然语言内容。没有稳定结构，也没有“模型推断 / 人工确认 / 事实”的边界。structured analysis schema · evidence refs · confirmation status · reviewer
条件性导入字段覆盖率可以记录解析错误和 Artifact。没有 expected-field 清单、字段级 validation result 和 parser version。manifest · expected schema · validation finding · parser/schema version

C / DASHBOARD LAYERS

差距落在看板的哪一层

四层页面并不是同一种数据：管理聚合、问题诊断、改进闭环和任务证据分别需要不同权威来源。

L1 / MANAGEMENT

整体运行情况

  • 任务数、完成率、活跃用户
  • 一次性准确率、耗时、Token
  • 代码量分布与 Top 改进

主要缺口：组织、Task、执行结果、代码产出、质量 verdict

L2 / DIAGNOSIS

执行效率 / 改进分析

  • 四阶段投入与产出
  • 受影响任务及比例
  • 当前判断与证据入口

主要缺口：阶段 taxonomy、Token、output fact、issue 分母

L3 / IMPROVEMENT

Self-Improving

  • 问题、现象、根因、措施
  • Cards 与 Knowledge Units
  • 预期效果与实际效果

主要缺口：intervention、知识消费、复测与归因边界

L4 / EVIDENCE

Task / Session 证据

  • Task、Spec、Session、问题
  • 阶段 Token、耗时、产物
  • Step6 报告和原始证据

主要缺口：身份关系、attempt、阶段事实与证据血缘

进入实现前，最少补齐四组事实

这不是要求立刻增加四套服务，而是要求在一个版本化输入合同中把身份、执行、质量与发布关系说清楚。

EVIDENCE BOUNDARY

这是一份合同差距评审，不是真实数据接入验收。

当前仓库只证明看板希望展示哪些字段：页面本身是静态夹具，刷新、导出和 TAR 上传均为浏览器内模拟。仓库中没有真实的 Upload / Processing / Analytics / Dashboard Service，也没有 PostgreSQL、NFS 或运行时解析链路。

当前仓库还没有 generate_upload_data.py、真实 upload_payload.json 样本或真实 TAR。因此本页对“已有字段”的判断来自架构方案文本，仍需回到生产者实现和真实样本复核。
